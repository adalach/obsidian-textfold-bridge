# Developing TextFold Bridge

## Build and test

```bash
npm install
npm run build   # typecheck, then a minified main.js
npm run dev     # an unminified main.js with an inline source map, for debugging
npm test        # the logic tests in test/
npm run lint    # eslint with Obsidian's plugin review rules (eslint-plugin-obsidianmd)
```

Obsidian loads `main.js`, `manifest.json` and `styles.css` from `<vault>/.obsidian/plugins/textfold-bridge/`. Each build copies the three files there: into the folder named by the `TEXTFOLD_BRIDGE_PLUGIN_DIR` environment variable, or else into `~/Documents/Obsidian Vault/.obsidian/plugins/textfold-bridge/` when that vault's plugins folder exists. After a rebuild, run `obsidian plugin:reload id=textfold-bridge` (the Obsidian CLI; add `vault="<name>"` when more than one vault is open) or turn the plugin off and on under **Settings → Community plugins**.

## Against a running TextFold

Run TextFold from a clone of its repository, with the clone as its data folder, so it reads and writes only the clone's own test library:

```bash
cd <textfold clone> && TEXTFOLD_NO_MODELS=1 TEXTFOLD_DATA=<textfold clone> python3 -m textfold serve --port 3017
```

`TEXTFOLD_NO_MODELS=1` makes it find no model, so Fold and Refold run through without a model call (the document reads as written, and the sidebar says so); leave it out only to test folding with the model, which costs. The server writes `server.json` into the clone: name the clone under **TextFold run from source** to test discovery, or rely on the default port. TextFold's desktop app picks a free port from 31917 up and keeps your own library; test against the clone, not against it. Documents a test folds land in the clone's `papers/`; delete them, `server.json` and `library.json` afterwards. One-off check scripts go in `temp/`, which is git-ignored.

Drops are tested with a synthetic `DragEvent` carrying a `DataTransfer` (`new DataTransfer()`, `setData(...)`) dispatched on the test note's `cm.contentDOM` at `cm.coordsAtPos(...)`, and pastes with a `ClipboardEvent`; check first that the test note is the active one. A real drag from TextFold's app cannot be automated.

When testing commands through the Obsidian CLI, call the plugin with an explicit file (`app.plugins.plugins['textfold-bridge'].folds.fold(file)` to export, `.openFold(file)` for the fold view) rather than running **Fold this note** or **Export this note to TextFold** by id: a command acts on whatever note is active, which may be someone else's while Obsidian is in use. If you must run one by id, activate the test note and run it in the same `eval`, with nothing awaited in between. The fold view's motion is tested with real input events through `obsidian dev:cdp` (`Input.dispatchMouseEvent` with `type: "mouseWheel"` and `modifiers: 4` for ⌘ + scroll, `Input.dispatchKeyEvent` for the keys 1 to 5); take `dev:screenshot`s only while the fold view is the tab in front.

## How it works

`src/main.ts` only wires the parts together and keeps the plugin's data: the settings and, under `folds`, one record per folded document (`FoldRecord`: the note, the hash of the text sent, the language, the last job).

Pure modules without runtime imports from `obsidian`, tested in `test/`:

- `src/links.ts` parses and builds `textfold://open?paper=…` links (`t=<turn>`, up to three digits, only with `n=`, and `to=<paragraph id>`, `[\w.-]+`, only with `u=`, as TextFold's `desktop/links.js` takes them; the reader's hash gets `#u=…&to=…`, and the reader lights up every paragraph from u to to), maps one to the reader's address (`<server>/p/<id>?lang=<code>#n=<note>&t=<turn>&u=<paragraph>&s=<section>&level=<name>`; the reader reads `#t=` after `#n=` and scrolls the conversation to that turn; the reader reads each of `#n=`, `#u=`, `#level=` on its own, so a link with both a note and a paragraph still lands on the paragraph when the note is gone), finds the documents a note refers to in its `textfold:` property and its text, and adds or removes an id in that property.
- `src/server.ts` finds TextFold: `dataFolders()` follows TextFold's own `store.app_data()`, `parseServerFile()` accepts only a `textfold/server` file of version 1 on `127.0.0.1`, and `resolveServer()` takes the first `server.json` whose process still runs (`process.kill(pid, 0)`) and whose URL answers, else the default port. The client puts the **TextFold run from source** folder before the system's data folder.
- `src/notes.ts` reads `GET /api/papers` (with `citekey` when TextFold lists one) and `GET /api/notes/<id>` (TextFold's `docs/notes-format.md`, including `anchor.lost` after a refold) leniently.
- `src/doc.ts` reads `GET /api/doc/<id>` (the `textfold/doc` format, `docs/format.md`): section names as the reader writes them, each unit's text per level, reading order and the reader's cite labels (`§3 ¶2`). `DocIndex.range(u, to)` is the paragraphs of a range in reading order (either way round), `withSubsections(id)` a section and the deeper sections after it up to one at its depth, and `sectionText()` a section as TextFold's reader drags it by its heading (blocks separated by blank lines: summary and `- ` paragraph lines at Key, Takeaway and Topic, a block per paragraph at Full and Brief, each subsection's name before its own); hover previews and filled-in bare links use it.
- `src/notesMarkdown.ts` groups notes by section in reading order and writes the imported block in the style of TextFold's `notesMarkdown` (reader.js); `replaceBlock()` swaps only the text between the two markers.
- `src/drag.ts` reads what TextFold puts on a drag or the clipboard, in order `application/x-textfold+json`, the same JSON in a `data-textfold` attribute of the `text/html`, or a lone `textfold://` link in `text/uri-list` or `text/plain` (filled in from `/api/doc` and the notes by `itemFromLink`), and writes the callout, quote or link a drop inserts. The JSON is TextFold's `textfold/drag` version 1 (`dragData` in its reader.js): for a note `text` is the reader's words or else the passage, `quote` the passage, `comment` the reader's words; for an Ask `text` is the last answer in one sentence and `comment` the question; a section dragged by its heading has `heading` ("2.1 Method") and its text in blocks, a selection over several paragraphs the link `u=<first>&to=<last>`, and both `units` (the paragraphs, in reading order). `formatItem` keeps such text's lines: in a callout or quote every line quoted and blank lines as `>`, in Text a bold heading line and the lines as they came, which `drop.ts` puts on lines of their own even among words. In such text a line starting like `2.1 Setup` is written `2\.1 Setup` (`keepOutOfLists`): after a list, Obsidian draws a line that starts with digits, a dot and a digit, and the lines after it, inside the list's last item; escaped it reads the same. Rendering is checked off screen with the static `render` of `MarkdownPreviewView`'s parent class (`Object.getPrototypeOf(view.previewMode.constructor)`), since `obsidian` cannot be required in an `eval`. The link in it is parsed and written anew, so a drop only ever inserts a `textfold://` link to its own document, and a `[[…]]` in it never becomes a wikilink (citations in the model's words become reader links).
- `src/citations.ts` finds every `textfold://` link in a note's text (Markdown links, `↗` icon links, bare addresses; not in front matter or code), with its offsets, line and its own words (for a `↗` or "Open in TextFold" link, the words it stands by), says what each cites from the doc JSON and the notes (`citedText`, `citedSection`), and groups them by the note's headings (offsets from the metadata cache) or by paper and section.
- `src/langs.ts`: TextFold's languages (`GET /api/langs`, either `[{code, name}]` or `{code: name}`; until a TextFold answers, the list of its `textfold/langs.py`), the reader's language in `GET /api/settings` (`lang`), and the language to fold in: the setting, or for **TextFold's language** the reader's, else `en`. `src/stored.ts` migrates saved settings (0.4's `foldLang` becomes `language`).
- `src/fold/align.ts` (Apache-2.0, adapted from TextFold's reader.js, tokens.py and ladder.py): TextFold's tokenizer, and for each unit of the doc JSON the pieces of each level with ids that persist across levels (`<unit>:<token>`): Full all sentences, Brief the evidence sentences with gaps, Key the model's words each taking the id of the author's word it matches (a longest common subsequence of normalized words over the Brief sentences), Takeaway the head of Key, Topic a run of Takeaway. A highlight is marked at the note's `anchor.tokens` when they still read as its passage, else where its passage is found. `alignRendered()` matches the words of a rendered paragraph to a unit's tokens, so Full's words (Obsidian's rendering) carry the same ids.
- `src/fold/blocks.ts`: the note's blocks from the metadata cache's `sections` (or by blank lines), their words as TextFold read them (`plainText`, through `flattenNote`), and `mapUnits()`: TextFold's sections to the note's headings by their words, in order; each paragraph to the first block, at most 8 ahead of the last, holding 60 % of its words (a list block can hold several list items); a caption to the next block that is only a picture.
- `src/flatten.ts` flattens a note for folding (outside code: wikilinks, comments, callouts, block ids, highlight marks) and hashes what is sent. `imageRefs()` lists the pictures a note embeds (outside front matter, code and comments); `flattenNote()` puts in each one's place what it is given for it (fold.ts gives vault pictures as `![alt](data:image/…;base64,…)`), keeps web pictures and data URIs, and drops the rest.

`src/client.ts` is the only code that makes requests: `requestUrl` to `127.0.0.1` only, queued one at a time, each given up after 2.5 s (the alive check, `GET /api/models`), 8 s (reads) or 30 s (an import). `requestUrl` goes through Obsidian's main process without an `Origin` header, which TextFold's check on POSTs accepts. A document's doc JSON is cached for the session and forgotten when it is folded again; an address that answered is reused for a minute.

`src/fold.ts` is **Export this note to TextFold**, and what **Fold this note** runs first when the note has no document or changed. `prepare()` reads the note, resolves each embedded picture as Obsidian does (`getFirstLinkpathDest` from the note's path, else a path relative to its folder), reads PNG, JPEG, GIF and WebP files up to 15 MB as base64 data URIs (cached by path, modification time and size), which TextFold's Markdown import (`local.Images._read`) stores in the document's `img/`, and counts what went along and what was left out for the notice. The hash covers the data URIs, so a changed picture shows as "changed since folding". Then a first fold asks once (it sends the note and uses TextFold's model), then `POST /api/import {name, text}`, `processFrontMatter` adds the id, and `POST /api/generate`; a refold is `POST /api/import {name, text, id}` (409 busy, 404 gone: the id leaves the property) and a generate with `force`. While a fold runs it follows `GET /api/jobs` every 1.5 s and stops when the job ends. `state()` tells the sidebar: folding, changed since (the hash differs), failed, or folded; a document stored without levels (`provenance.local`) is shown as such and Refold folds it.

`src/fold/view.ts` is **Fold this note**'s view (`textfold-fold`, a `FileView` on the note; `main.ts` `openFold()` puts it in the tab that shows the note). It renders each non-heading block once with `MarkdownRenderer` and keeps the elements, reads `GET /api/doc/<id>?lang=` and the notes, and draws the document at a level: Full is the rendered blocks (each paragraph's text nodes are wrapped into word spans by `alignRendered`), Brief to Takeaway are rows of word pieces per unit, Topic is the map. When fewer than half of TextFold's paragraphs map to the note's blocks (a translation, or a note folded in another language than its own), Full is drawn from the doc JSON's own text like the other levels (`ownWords`). Only rows near the viewport (600 px) get word spans; the others stay plain text until scrolled near (`heat()`). Only a view opened by the command (`auto` in its state) exports a note by itself; a restored view only offers the button. The doc JSON is kept in `app.saveLocalStorage` (`textfold-bridge-fold:<id>:<lang>`, with the note's hash) for when TextFold is not running. `src/fold/motion.ts` (Apache-2.0, adapted from TextFold's reader.js) moves the words: it measures the word spans near the viewport, lets the view draw the new level, keeps the anchor paragraph in place by scrolling, and animates each word from where it was (FLIP with the Web Animations API), with fading ghosts for words that left. A ⌘/Ctrl + scroll, a pinch or the slider scrubs paused animations (`currentTime`) and springs to the nearer level when it stops; `prefers-reduced-motion` skips the motion. The view's classes are its own (`tfb-mcard`, `tfb-folded`, …): `tfb-card` and `tfb-fold` belong to the hover card and the sidebar.

`src/importer.ts` is **Import notes**: per document `GET /api/notes`, `GET /api/doc`, then the note imported before, found anywhere in the vault by `isImportedNote()` (its `textfold` property is the id and it holds the block's start marker; one in the target folder first), or else a new note (named by `noteFileName()`) in the folder `importTarget()` chooses: the folder setting, the folder of the note the import starts from, or the vault's own, with the folder setting as the fallback when no note is open; `vault.process` replaces the block only when it changed, and `processFrontMatter` sets only the properties the import owns.

`src/drop.ts` handles Obsidian's `editor-drop` and `editor-paste` in any Markdown editor: when `readTransfer()` finds a TextFold item it calls `preventDefault()` at once (else Obsidian handles the event as always), takes the position nearest the pointer from CodeMirror's `posAtCoords(…, false)` (the precise form gives null beside a short or empty line) (the cursor for a paste), and inserts the block on lines of its own, splitting a paragraph it was dropped into, or the link among the words with spaces. The sidebar's rows put the same data on their `dragstart` (`setTransfer`).

`src/icon.ts` holds TextFold's logo (the reader's three bars, in currentColor), registered with `addIcon` as `textfold-logo`: the sidebar's view icon, the commands' icon, the sidebar's "Open in TextFold" buttons, the `[!textfold]` callout's `--callout-icon` (Obsidian resolves a callout icon with `setIcon`, so a registered id works) and the icon of `[↗](textfold://…)` links. The callout's colour is `var(--callout-example)`, the theme's own "example" callout colour in whatever form the theme writes it: an rgb triplet in Obsidian's default theme, hex in Minimal (where an rgb variable such as `--color-cyan-rgb` leaves the callout without a background). `src/iconLinks.ts` draws those links as the icon: a Markdown post-processor in Reading view (the rendered `<a>` gets the logo), and in Live Preview a CodeMirror `ViewPlugin` that adds one mark decoration and no widget: `tfb-lp-icon` on the `↗` label. At `Prec.highest` it is the innermost span, around the glyph alone, inside Obsidian's `.cm-link > .cm-underline`; styles.css draws it as the logo (a CSS mask of the bars in `--text-accent`, the glyph transparent) and takes the background arrow and padding off the `.cm-url.external-link` span Obsidian puts in place of the address, for the arrow that follows the icon's link with no other link in between (a `:has()` sibling selector: that span is outside any mark on the link). Obsidian keeps rendering and handling the link, so a click opens it through `window.open`, which `opener.ts` takes. No mark where the selection touches the link (it shows as written), in fenced code or in an inline code span. Until 0.5.0 a `Decoration.replace` widget at `Prec.highest` stood in for the whole link, next to Obsidian's own widgets for it; a freshly dropped callout was seen drawn one letter per row after the first click into it (which switches Live Preview from the callout's widget to its source lines), which could not be reproduced with synthetic drops and CDP clicks. `src/hover.ts` previews the icon on a hover alone, other editor links with Cmd/Ctrl held.

`src/opener.ts` opens links. Before opening, it checks the document against `/api/papers` (kept for 30 s by the client): one the running TextFold has not gets a notice instead, since TextFold would show its home screen. Obsidian opens an external link through `window.open` both in Live Preview (`triggerClickableToken`: the link is a CodeMirror token, not an `<a>`) and in Reading view (`onExternalLinkClick` on `a.external-link`, whose `textfold:` href the renderer keeps). For a scheme other than http(s) and `obsidian:` the main process asks before passing it to the system; an http(s) URL opened with the target `_external` goes to the default browser instead of Obsidian's web viewer. So a capture-phase click handler takes `a[href^="textfold:" i]` in every window, and a wrapper around `window.open` takes `textfold:` URLs from Live Preview. Everything else passes through. On unload the wrapper is removed if it is still the outermost one, and otherwise turns into a pass-through.

`src/hover.ts` shows hover previews in Obsidian's own `HoverPopover` (page previews only show vault files): a mouseover on `a[href^="textfold:"]` in every window, and in the editor a CodeMirror `mouseover` handler that, with Cmd/Ctrl held, finds the Markdown link under the pointer in the line's text (the address is not in Live Preview's DOM). It shows a paragraph at the link's level or Takeaway, a section's title and summary (`s=`), a note, the document's title, authors and note count, or that TextFold has no such document.

`src/jump.ts` goes to a citation: in the note's tab (the most recent one that shows it, else a new one), the editor gets the cursor on the link, `EditorView.scrollIntoView` to the middle and a mark decoration (`flashField`, `.tfb-flash`) for 1.6 s, so nothing is selected that typing could replace; Reading view gets `setEphemeralState({line})`, which scrolls there and lights the line, and the rendered link (the nth with that address) is lit too.

`src/view.ts` is the sidebar (`textfold-notes`), in two parts behind a switch remembered in the settings (`sidebarTab`): **In this note**, the citations (`citationsGroup`: by heading or by paper; a row's click calls `jumpTo`, its icon opens TextFold, its hover previews through `LinkPreviews.attach`), and **In TextFold**, the documents' notes as before. Both use the same requests: per cited document its notes and doc JSON; an edit that leaves the set of documents unchanged only re-reads the note's text and the metadata cache. It refreshes on `file-open`, when Obsidian's window gets the focus back (at most every 3 s, only while the view is shown), when the note's set of documents changes, when a fold ends, and from its refresh button; an edit of a folded note only recomputes its fold state. Notes are grouped under their sections' names; a lost note is in italics with a warning mark. Hovering a row for 350 ms shows a card beside the sidebar with the passage, the reader's text and the conversation, rendered with `MarkdownRenderer` into a child component that is unloaded when the card hides. Server text goes in through `setText` and `MarkdownRenderer` only. `src/picker.ts` is the **Insert link to a TextFold paper** picker. `src/settings.ts` declares the settings with `getSettingDefinitions()`, so they appear in Obsidian's settings search; the connection row is rendered by hand for its **Test connection** button.

The plugin reads a file outside the vault with Node's `fs`, so `isDesktopOnly` is `true`.

## Release

Nothing is released. The id `textfold-bridge` is a working name; settle it before a first release, because an id cannot change once released.

1. `npm version <x.y.z>` sets the version in `package.json`, `manifest.json` and `versions.json` (through `version-bump.mjs`), commits, and tags the commit `x.y.z` without a `v`.
2. `git push --follow-tags` starts `.github/workflows/release.yml`, which checks that the tag matches `manifest.json`, builds, tests, lints and opens a draft release with `main.js`, `manifest.json` and `styles.css` attached.
3. Review the draft on GitHub and publish it.
